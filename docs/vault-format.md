# Vault format

The vault is the contract: MoneyTracker is replaceable, the files are not. Everything here is
plain hledger syntax; the app only refuses what it cannot represent exactly.

## Layout

```
<vault>/
  index.ledger            entry point (options + declarations + includes)
  accounts.ledger         account declarations, `; type:` tags
  prices.ledger           `P` directives
  budgets.ledger          `~ monthly` recurring blocks
  recurring.ledger        declared schedules: salary, loan, subscriptions (included)
  rules.ledger            MoneyTracker rules (never included by index.ledger)
  goals.ledger            plan / FIRE assumptions (never included)
  recur.ledger            `; skip:<id>@<limit>` recurring decisions (never included)
  <year>/
    <year>.ledger         includes the month indexes of that year
    <year>-<MM>.ledger    includes the day files of that month
    <year>-<MM>-<DD>.ledger  one day of transactions
  .bak/                   snapshots taken before every rewrite
  .sync/                  sync state: `index.json` (last agreed hashes), `trash/` (git-ignored)
```

`.sync/` is device-local: it records the hash of every file the last sync agreed on, which is what
lets the next run tell "changed here" from "changed there". It is not part of the ledger, not
uploaded, and git-ignored, so deleting it only costs one full comparison.

The include chain is created lazily: a transaction written on 2026-10-04 creates
`2026/2026-10-04.ledger`, adds `include 2026-10-04.ledger` to `2026/2026-10.ledger`, adds
`include 2026-10.ledger` to `2026/2026.ledger`, and adds `include 2026/2026.ledger` to
`index.ledger` if it is missing. Every step is idempotent and no file is ever truncated.

A transaction is only visible to the reader when that whole chain exists — a hand-written day file
that nothing includes is ignored (this is also how `hledger` behaves).

## What `index.ledger` includes

`accounts.ledger`, `prices.ledger`, `budgets.ledger`, `recurring.ledger` and the year files. Two files
stay out on purpose, and one of them is only out for the app's own reading — see below.

### Rules are not included

`rules.ledger` is read by the application directly and is deliberately absent from
`index.ledger`. Capture expands a rule into real postings and writes those, together with a
provenance comment. If the rules file were included, `hledger --auto` would apply the same rule a
second time and the balance would differ between the app and the CLI.

`recurring.ledger` **is** included, because those blocks are `~` periodic transactions: hledger
ignores them unless you ask for `--forecast`, so `hledger -f index.ledger reg --forecast` shows the
planned salary next to the real one. What would break is MoneyTracker's own reading of them — the
budget envelope scan, the cash flow forecast and the payoff estimate all skip `recurring.ledger`
explicitly, so a declared salary never turns into an envelope and never counts a month twice.

## Transaction shape

```ledger
2026-10-04 * 星巴克  ; txn:01JA3KQ70SEED0005 rule:r-star query:desc:星巴克 :coffee:
    expenses:food:coffee         31.50 CNY
    expenses:food                13.50 CNY
    assets:wallet:alipay        -45.00 CNY
```

Conventions the app maintains:

| Tag | Meaning |
| --- | --- |
| `txn:<id>` | stable identifier (UUIDv7-shaped) written by the app on create and on first edit |
| `rule:<id>` / `rule:none` | which rule produced the postings; `none` means no rule matched |
| `query:<raw>` | the capture text that produced the rule expansion |
| `recomputed:<ISO8601>` | appended when the postings were regenerated by `rule_recompute` |
| `:tag:` / `key:value` | user tags, printed in hledger's canonical form |

Transactions without `txn:` (written by hand or by another tool) get a pseudo id derived from
`blake3(relative path + byte offset + date + payee)`; the first time the app writes to such a
transaction it also writes a real `txn:` tag. Pseudo ids are stable as long as the file is not
reflowed above them.

## Grammar subset

Accepted:

- comments: `;` `#` `%` `|` `*`, plus `comment` … `end comment` blocks;
- directives: `include`, `!include` (missing files are silent), glob patterns (`*`, `?`, `**`),
  `account` (with `; type:A|L|E|R|X` and other tags), `commodity`, `D`, `Y`, `P`,
  `~ <period>` blocks, `= <query>` auto-posting rules;
- transactions: `DATE[=DATE2] [*|!] [(CODE)] DESC [; COMMENT]`, any number of postings, each with
  optional status marker, virtual `(account)` or balanced-virtual `[account]`, elided amount,
  `@` unit price, `@@` total price, `= AMOUNT` balance assertion and a comment;
- amounts: prefix or suffix commodity, thousands separators, decimal comma, `-`/`+` signs,
  `70.00%` percentages in rules.

Rejected with `file:line:col: error[code]: message`:

| Code | Cause |
| --- | --- |
| `core.parse.unsupported_amount_expression` | arithmetic like `(10 + 5)` in an amount |
| `core.parse.unsupported_lot_price` | lot/cost annotations `{…}` |
| `core.parse.unsupported_conversion` | `C` / `N` conversion directives |
| `core.parse.unsupported_csv_rule` | `csv:` / `csv file.csv` rules |
| `core.parse.orphan_posting` | an indented line outside a transaction or rule |
| `core.parse.bad_date`, `bad_amount`, `amount_no_digits` | malformed date/amount |
| `core.parse.unknown_directive` | anything else at top level |

Warnings (loading continues): `core.parse.unindented_posting` for de-indented `~`/`=` postings,
`balance.not_zero` for an unbalanced transaction from an external file.

### Periodic blocks and budgets

`budgets.ledger` holds `~ <period>` blocks. Only the **positive** leg is an envelope; the negative
leg exists to balance the block.

- an `X` (expense) account is a **spending envelope**: `actual` is what was spent this month,
  `remaining` is budget minus spend, `ratio` is spend / budget;
- an `A`/`L` account is a **savings goal**: `actual` is the net base-currency amount that moved
  into the account this month (deposits positive, withdrawals negative), `remaining` is how much
  is still missing, `ratio` is progress.

Envelope accounts do not have to exist in the ledger yet; the kind is resolved from the nearest
known parent, then from the configured top-level name map (`assets:` → A, `expenses:` → X, …), so a
planned `assets:invest:retirement` envelope works before its first transaction. Periods are scaled
to a month: `yearly` ÷ 12, `quarterly` ÷ 3, `weekly` × 52/12, anything else counts as monthly.
Forecasts use the monthly envelope total (see `docs/architecture.md`).

Postings under `~` and `=` blocks that lost their indentation are still accepted, but each one
raises `core.parse.unindented_posting` as a **warning** — hledger requires the indentation, so the
file is not portable until the block is re-indented. Transactions themselves stay strict:
unindented lines under a transaction header are not postings.

Each transaction is balance-checked per commodity while loading. A transaction in a file the app
wrote must balance exactly (one elided amount is filled in from the others); an unbalanced
transaction in an externally written file is reported as a warning and marked read-only rather than
being "fixed".

## The plan file

`goals.ledger` is optional and, like `rules.ledger`, is **not** included by `index.ledger` — hledger
never sees it. One directive per line:

```ledger
assume  ; return:6% inflation:2.5% reserve:6
pool    ; accounts:assets:invest,assets:cash
alloc   ; equity:60% bond:20% cash:20%
goal fire 财富自由 ; swr:4%
goal account 退休金 ; account:assets:invest:retirement target:1000000.00 CNY by:2040-01-01
debt 房贷 ; account:liabilities:mortgage rate:3.15% payment:8200.00 CNY
```

- `assume` — nominal return and inflation are percentages (`6%` or `6`), `reserve` is a month count.
- `pool` — comma-separated accounts (subtrees count); defaults to `assets:invest`.
- `alloc` — `class:share%` pairs matched against `; class:<name>` tags on account declarations.
- `goal fire` — a label plus optional `swr:`; `goal account` — `account:`, `target:`, optional `by:`.
- `debt` — `account:`, `rate:`, `payment:`; the balance is read from the ledger, and extra-payment
  scenarios are simulated, never written.

Unknown directives produce `plan.unknown_directive` diagnostics with line numbers and are shown in
the 规划 view instead of failing the load.

## Sync metadata

Sync keeps its own state under `.sync/`; nothing about it enters the ledger:

```json
{
  "schema": 1,
  "vault": "3f9c…",
  "device": "9a1c…",
  "last_sync": "2026-11-20T02:46:11Z",
  "files": { "2026/2026-11.ledger": "b3f1…", "index.ledger": "77aa…" }
}
```

`files` maps a vault-relative path to the blake3 hash both sides agreed on at `last_sync`. The same
manifest, plus a per-file hash, size and mtime, is stored in the bucket as
`<prefix>/manifest.json`, and the file contents themselves live at `<prefix>/blobs/<hash>` (content
addressed, so an unchanged file is never re-uploaded). A file removed by a sync is moved to
`.sync/trash/<timestamp>/<path>`, not unlinked.

## Recurring decisions

`recur.ledger` (not included by `index.ledger`) holds the "not this cycle" answers:

```
; MoneyTracker recurring-transaction decisions — read by the app, never included by index.ledger.
; skip:c-1a2b3c4d@2026-10
```

Transactions written by the automation carry `recur:<id>@<YYYY-MM>` next to their `txn:` tag; the tag
is engine-owned metadata, so the editor hides it and every rewrite preserves it.

## Declared schedules

`recurring.ledger` (included by `index.ledger`, so `--forecast` sees it) states the money that is *supposed* to happen every
month, so the 日程 view can show it as a calendar instead of leaving it to the pattern detector. It is
plain periodic syntax:

```
~ monthly from 2025-08-05  ; id:salary-main label:工资 kind:salary
    income:salary                        -30,000.00 CNY
    income:benefit                       -12,300.00 CNY  ; 公司缴纳侧合计
    assets:cn:fund                         4,200.00 CNY
    assets:cn:pension                      7,200.00 CNY
    assets:cn:annuity                      3,600.00 CNY
    expenses:insurance:medical             3,000.00 CNY
    expenses:insurance:unemployment          300.00 CNY
    expenses:insurance:injury                150.00 CNY
    expenses:insurance:maternity             300.00 CNY
    assets:bank:cmb                       23,550.00 CNY  ; 到手
```

- The header comment holds whitespace-separated `key:value` metadata: `id:` (defaults to the label plus
a hash of it), `label:`, `kind:` (`salary` / `loan` / `income` / `expense`, display only),
`enabled:false` to keep a template but stop suggesting it, and `settle:<account>` as an override.
- `monthly from <date>` is the supported period, and the day-of-month comes from that date — the same
rule hledger applies, so the file stays valid outside the app. A day past the end of a month clamps to
the last day (`from 2026-01-31` → 2 月 28/29). `weekly from <date>`, `quarterly from`, `yearly from`
and a bare `monthly` (the 1st) also work. The app-only `day:<1-31>` token is still parsed for older
files but hledger rejects it, so generated text no longer uses it.
- **The last posting is the cash leg.** It decides the 现金流 figure on the card, and it may omit its
amount — the engine fills it so the block balances, exactly like a hand-written transaction.
- Nothing is booked by merely declaring a template. 记入 writes one occurrence through the normal
day-file path and tags it `sched:<id>`; `设置 → 自动化 → 自动记入固定收支` (the same switch the pattern
detector uses) makes the monthly maintenance run book whatever is due that month.
- `; sched:<id>@<YYYY-MM>` lines in `recur.ledger` mark a month as skipped, so 跳过 survives a reload.

## Imported transactions

A row written by the statement importer is an ordinary transaction block with two extra tags:

```
2026-10-03 * 星巴克  ; txn:01a1… import:2026-10-05T09-12-00 ref:4200001234567890 :coffee:
    expenses:food:coffee                32.00 CNY
    assets:bank:cmb                    -32.00 CNY
```

- `import:<batch>` is the batch id (a timestamp), so one import can be reviewed or reverted as a unit.
- `ref:<id>` is the bank's own reference when the export carries one; it is what makes dedupe robust
  when a statement is re-exported with different column order.
- Dedupe itself uses the fingerprint `blake3(account|date|amount|commodity|payee)` over the parsed
  transaction, not the tags, so hand-typed entries are protected too.

Both tags are engine-owned metadata: they are hidden from the editor and preserved by every rewrite
(see `docs/architecture.md`).

## Editing rules

- A rewrite touches one byte span (the transaction block plus one blank line) and is preceded by a
  snapshot and a hash check; see the write-safety list in `README.md`.
- Deleting a transaction removes the block and one adjacent blank line so repeated deletions do
  not leave a column of empty lines.
- Adding a tag rewrites only the header comment; posting comments are preserved verbatim.
- Anything the app does not need to touch is copied through unchanged, including formatting the
  printer would not produce (e.g. aligned columns written by another editor).

## Accounts and types

`accounts.ledger` tags drive the role logic in capture:

```ledger
account assets:wallet:alipay   ; type:A
account liabilities:card       ; type:L
account income:salary          ; type:R
account expenses:food          ; type:X
```

Without a declaration the top-level segment decides: `assets`→A, `liabilities`→L, `equity`→E,
`income`/`revenues`→R, `expenses`→X (configurable). Unknown roots are `U` and never chosen as a
funding account automatically.
